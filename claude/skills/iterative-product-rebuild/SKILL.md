# Iterative Product Rebuild — методология

Этот skill активируется когда пользователь хочет **системно и пошагово** построить или пересобрать продукт/систему/модуль с нуля или с переработкой. Не для багфиксов, не для маленьких добавлений — для **больших трансформаций** где нужна рамка.

## Когда активировать

**Активируй**, если пользователь:
- Явно ссылается на <проект> или образец работы — «как мы делали раньше», «по этому принципу», «iterative rebuild», «в той рамке».
- Приносит **большой контекст** (несколько абзацев про бизнес, продукт, существующее состояние) и просит структурного подхода.
- Говорит «давай построим / пересоберём / спроектируем» **продукт или систему** (не feature).
- Просит «провести интервью», «составить план фаз», «сделать ADR-набор».

**НЕ активируй**, если:
- Конкретный багфикс или маленькая задача.
- Уже идёт работа в рамке (не нужно перезапускать skill).
- Технический вопрос про конкретную библиотеку или API.

При активации — ответь коротким acknowledgment и сразу веди по Phase 0 (framing). Не штампуй фазы по списку — каждая фаза должна быть оправдана для конкретной задачи.

## Образец

Полная переписка одной такой работы (<проект> — пересборка co-pilot системы для Я.Директа из чистого листа до live прода через ~6 месяцев работы) живёт в:

`~/<проект>/docs/learning/adevolver-rebuild-session.md` (711 KB, 1070 сообщений).

Это **референс** не для копирования слово в слово, а для понимания **формата работы**: как меняется тональность от phase 0 до phase N, как формулируются ADR, как структурируются executor dispatches, как ведутся memory updates.

## Шесть фаз

Не все нужны для всех проектов. Для мелких — можно слить 2-3 фазы в одну. Для больших и с серьёзными деньгами на кону — каждую тщательно.

### Phase 0 — Distillation (интервью с владельцем)

**Цель**: вытащить из головы владельца контекст которого нет в коде/документах.

**Действие**: прежде чем писать что-то — провести **сессию вопросов**. Не «опросник из 5 пунктов», а живой разговор:
- Что цель в одной фразе?
- Что вне фокуса?
- Кто пользователь и в каких ситуациях?
- Какая бизнес-модель / откуда деньги / какая unit-экономика?
- Что уже есть (если пересборка)?
- Какие принципиальные ограничения / красные линии?
- Что НЕ работало в прошлом?

Если владелец сам — это ты (CEO случай), то делается **самораспаковка**: создаётся документ с этими вопросами, пользователь голосом отвечает, ответы становятся точкой опоры.

**Артефакт**: `docs/distillation-session.md` или `intake.md`. **До этого фазы 1+ не начинаются.**

### Phase 1 — Framing (BMC / JTBD / Lean Canvas / CapabilityMap)

**Цель**: зафиксировать смысл проекта на стратегическом слое до любого кода.

**Действие**: для каждого фрейма (Business Model Canvas / Jobs-To-Be-Done / Lean Canvas / Capability Map / System Boundary) — отдельный markdown в `docs/strategy/`. **Не вместе** в один файл — это анти-паттерн (см. memory `feedback_essence_not_solution`).

Каждый фрейм даёт ответы на **разные** вопросы:
- BMC — экономика и партнёры.
- JTBD — для чего пользователь нанимает продукт.
- Lean Canvas — критические допущения и риски.
- CapabilityMap — что система должна уметь (без КАК).
- SystemBoundary — что НЕ в scope.

**Артефакт**: набор файлов в `CEO HQ/` или `docs/strategy/`. **Каждый отдельно подтверждается** владельцем перед фазой 2.

### Phase 2 — Roadmap + ADR set

**Цель**: разбить большое на milestones и зафиксировать архитектурные решения.

**Действие**:
- `docs/M{N}-roadmap.md` для каждого milestone (M1, M2, M3).
- 3-5 `ADR-{NNN}-{slug}.md` для **CEO-уровневых** решений (выбор технологии, паттерна, scope границы).

Принципы ADR:
- Один ADR = одно решение.
- Статус: `Accepted | Superseded by ADR-XXX | Deprecated`.
- Структура: Context / Decision / Consequences (positive + negative).
- ADR пишет не разработчик «потому что код такой», а владелец продукта «потому что бизнес такой».

**Анти-паттерн**: вписывать в ADR факты которые меняются («Strokov — 1760 лидов за 30 дней»). Факты — runtime данных, ADR — про принципы. См. `feedback_data_not_declaration`.

### Phase 3 — Sprint cycles

**Цель**: реализовать roadmap atomic спринтами.

**Действие**: каждый sprint = **один executor dispatch** с конкретным DoD:
- Список файлов.
- Конкретные миграции БД с номерами.
- Тесты что нужны.
- Commit message template.
- Verification checklist.

Главный принцип: **не штамповать**. Каждый dispatch — это **детальный brief 200-500 строк**, не «реализуй спринт N». Executor работает в одном куске контекста, поэтому ему нужны все детали явно.

После каждого спринта:
1. Применить миграции, rebuild.
2. Smoke test (curl или live UI).
3. Memory update если есть урок.
4. Sync с владельцем — короткий отчёт, ждать ОК или корректировки.

**Анти-паттерн**: «запущу 5 спринтов параллельно и потом разберусь». Они зависят друг от друга — последовательно.

### Phase 4 — Validation waves

**Цель**: убедиться что продукт **реально работает** для пользователя, а не «вежливо круто на созвоне».

**Действие**:
- **Симулятор реальных диалогов** — скрипт прогона N сценариев через реальный stack (HTTP/API). Не моки, не тесты — настоящая система.
- **AI-судья** — отдельный AI оценивает качество (5 параметров, 1-5 шкала) — даёт baseline score.
- **Findings consolidation** — топ слабых мест с приоритизацией.
- **Применить топ HIGH findings** атомарными коммитами.
- **Re-simulation** — проверить что метрики выросли.

Это **критический этап** который пропускают чаще всего. Без него продукт реально не работает, а кажется что работает.

### Phase 5 — Continuous improvement loop

**Цель**: после закрытия milestone-фазной разработки войти в режим постоянной эволюции.

**Действие**:
- **Memory feedback файлы** — каждый урок от пользователя сохраняется в `~/.claude/projects/.../memory/feedback_*.md`. Следующая сессия их подхватит.
- **Periodic re-simulation** — раз в месяц прогон симулятора и сравнение с baseline.
- **Post-mortem на каждый bug** — что сломалось, почему, какое правило выучить, в memory.

## Cross-cutting принципы

Эти повторяются в каждой фазе.

### 1. Data, не declaration

Никогда не зашивать факты про бизнес в код. Каждый «факт» в системе — это runtime запрос к источнику правды. Если ответ "я знаю" / "было в обсуждении" — это **не источник**.

См. memory `feedback_data_not_declaration`.

### 2. Strong session ДО tech fix

При технической проблеме сначала рамка / распаковка / понимание, потом код. Не лезть в Lego прежде чем понять, что собираем.

См. memory `feedback_strong_session_before_tech_fix`.

### 3. Approve first, write second

Декомпозиция / статусы / решения сначала в чат, артефакт ТОЛЬКО после approval. Walkdown в порядке 1→2→3→4, не прыжки в «острое».

См. memory `feedback_approve_first_artifact_second_and_sequential_walkdown`.

### 4. Мнение + обоснование + рамка

При разборе артефактов (документ/папка) не «как есть», а **мнение + обоснование + рамка** → владелец подтверждает или правит.

См. memory `feedback_opinion_with_frame`.

### 5. Самый низкий фрукт

Для нового пользователя — первая ценность через клон работающего benchmark'а, не «правильная стратегия». Сначала деньги, потом красота.

См. memory `feedback_lowest_hanging_fruit`.

### 6. Atomic executor dispatches

Каждый sprint = детальный brief (200-500 строк) для executor. Не «реализуй M3» а конкретный список файлов / SQL / тестов / verification. Executor работает в одном куске контекста и нуждается во всём явно.

### 7. Memory как живая часть процесса

Feedback'и сохраняются **по ходу разговора**, не задним числом. Каждый урок от пользователя — отдельный `feedback_*.md` файл. Следующая сессия их сразу подхватит.

## Anti-patterns (НЕ делать)

- **Писать код до Phase 1** — типичная ошибка. «Сначала прототип, потом подумаем» приводит к 5 переделкам.
- **Опросник вместо живого распаковочного разговора** в Phase 0 — пользователь засыпает после третьего вопроса. Нужна структура секций с преамбулами и подсказками.
- **Hardcoded факты в коде AI-слоя** — система мгновенно стареет и врёт. Только runtime из источника правды.
- **ADR на «как код выглядит»** — это документация кода, а не ADR. ADR — на «почему именно так с точки зрения бизнеса».
- **Один большой ADR на все решения** — не читается, не обновляется. Один ADR = одно решение.
- **Игнорировать Phase 4 валидации** — самая дорогая ошибка. Без симулятора нельзя сказать что продукт работает.
- **Симулировать «вежливо круто»** — оценщик должен быть либо отдельным AI с beam критериями, либо реальный пользователь который реально использует. Не «коллеги протестировали».
- **Memory feedback задним числом** — теряются нюансы, формализуется. Сохраняй по ходу.

## Шаблоны (для быстрого старта)

### Distillation session template (Phase 0)

```markdown
# Распаковочная сессия {продукт/проект/модуль}

> Цель: получить из головы владельца контекст которого нет в коде.

## Как пользоваться

[Инструкции владельцу: можно голосом, неформально, лучше точно по N блокам чем приблизительно по M]

## Блок 1 — {тема}

### Преамбула
[Зачем эти вопросы]

### Вопросы
**1.1** ...
**1.2** ...

## Блок 2 — {следующая тема}
...

## Если не получается ответить
[Приоритет блоков 1→2→3 для частичного ответа]
```

### ADR template

```markdown
# ADR-{NNN} — {one-line decision}

- **Status:** Accepted
- **Date:** YYYY-MM-DD
- **Связано с:** {другие ADR / memory feedback}

## Контекст

{2-4 абзаца почему решение нужно сейчас, какие альтернативы рассматривались}

## Решение

{Точная формулировка решения, без waffle}

## Последствия

Позитивные:
- ...

Негативные:
- ...

## Что НЕ делаем (явно)

- ...
```

### Sprint dispatch template (Phase 3)

```markdown
Задача — спринт M{N}.{M}: {one-line goal}.

## Контекст

[Где находимся: предыдущие commits, что есть для интеграции, актуальные ADR]

## Что в scope

### 1. {Файл/модуль/таблица}
[конкретные изменения]

### 2. ...

## Verification

- pytest collect + non-DB.
- ruff.
- docker compose config.
- НЕ rebuild — я делаю.

## Коммит и push

[Template коммит-message с разделом на каждое изменение]

## Принципы

[Cross-cutting напоминания + не выходить за scope]
```

## Когда позвать этот skill

При **продуктовом** разговоре («давай построим / пересоберём X»). Сразу скажи активируешь, дальше веди по Phase 0.

При **техническом** запросе («нужно добавить feature Y») — обычная работа, не активируй.

При сомнении — лучше задать один уточняющий вопрос «нужна структурная пересборка по образцу <проект> или это обычная задача?» чем активировать когда не надо.
