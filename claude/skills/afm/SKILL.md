# AFM — исполняемый протокол (v1.1, 17.07.2026)

Полная методология с обоснованием: `~/.claude/skills/afm/METHOD.md` (читай при спорных решениях). Здесь — только то, что ты ДЕЛАЕШЬ, по шагам. Отступление от протокола — только осознанное, с фиксацией причины в журнале прогона.

## Фаза 0 — применимость (2 минуты, честно)

НЕ применяй AFM и скажи об этом пользователю, если: задача < ~5 артефактов; правка в 1–2 файла; ресёрч без известной формы результата; сильно связное ядро без реальной ширины ≥ 3 независимых ветвей. **Проверь ширину честно с учётом общих ресурсов**: в проектах с общей БД (CRM, монолиты) узлы, пишущие в БД, во многом сериализуются — реальная параллель там 2–3 (файловые узлы: фронт, конфиги, тесты, доки), не 4–6. Если реальная ширина < 3 — прямое исполнение, оверхед графа больше выигрыша.

Норматив масштаба: ≤ ~15 узлов на один прогон одного оркестратора. Крупнее — иерархия: верхний граф из крупных блоков, каждый блок — отдельный AFM-прогон.

## Фаза 1 — компиляция графа

Создай в проекте `afm/<slug>/`: `plan.md` (реестр узлов+статусы), `passports/`, `handoffs/`, `journal.md`.

Шаги строго по порядку:

1. **Артефакты, не действия.** Разложи цель на конечные проверяемые состояния. Узел «исследовать X» запрещён — только «ADR по X принят». ≤ 20–30 узлов на уровень.
   **Чеклист 100% rule** (не «на глаз»): (а) для каждого требования задачи назови листовой узел, который его закрывает; (б) для каждого листового узла назови требование (нет требования = узел лишний); (в) composition двух узлов пересекается → дубль, слей или разграничь. Непокрытое требование = граф неполон.
2. **Рёбра.** Для каждой пары с ребром спроси: «изменится ли содержимое B, если A выйдет другим?» Нет — ребра нет. Ложные рёбра — главный убийца параллелизма.
3. **Циклы (DSM-проход), процедура:** выпиши все рёбра списком `A→B`. Для каждого ребра проверь обратное: влияет ли B на A (изменится ли A от иного B)? Пары с рёбрами в обе стороны = цикл. Цикл не выстраивать в цепочку: слей в один узел ИЛИ разорви артефактом-допущением (draft-контракт, стаб) + обязательный verify-узел «допущение подтвердилось» ниже по графу.
4. **Контракты — первыми.** Интерфейсы (API-спека, схема БД, типы, форматы) = первые узлы, tier A. Фиксируй минимум: интерфейс, не реализацию. Freeze до fan-out.
5. **Карта владения.** Каждому узлу — непересекающийся набор файлов/модулей. Пересечение карт = принудительное ребро сериализации. Общие точки (роутинг, конфиги, миграции, lockfile) — в отдельный ранний артефакт. Общий внешний ресурс (dev-БД, API-лимит) — сериализация или изолированный инстанс (честно оцени, что дешевле; см. Фазу 0 про ширину).
6. **Tier.** A (принимает человек, по поведению): контракты, схема БД, всё с высокой ценой распространения ошибки. B: автоматика + выборочный контроль.
7. **Критическая цепь — упрощённый расчёт, достаточный для Gate-0:** (а) longest path по рёбрам (сумма медианных оценок узлов); (б) + ожидание приёмки: каждый tier-A узел на пути ≈ +1 слот каденции; (в) rework-буфер = 30–50% от (а)+(б) — стартовый дефолт, утверждается на Gate-0, после первых прогонов калибруется журналом. Set-based узлы — доп. расход ПОВЕРХ буфера: (вариантов−1) × бюджет узла.
   Ориентиры бюджета узла (стартовые, калибруй по journal.md): контракт/ADR ~20K токенов, модуль кода ~50–100K, тест-сьют ~30–50K, интеграционный гейт ~40K.
8. **Rolling wave.** Полные паспорта — только у ближних 1–2 волн планирования; дальше planning-packages (цель + бюджет). Discovery-зоны — только spike-узел, продолжение графа после его приёмки. Паспорта волны N+1 дописывай, когда ≥50% узлов волны N приняты (их HANDOFF уже есть); узел без паспорта не стартует, даже если входы готовы.

### Шаблон паспорта узла (`passports/<id>.md`)

```markdown
# <id> — <название артефакта>
- purpose: <ЦКП одной фразой>
- composition: <что именно: файлы/таблицы/эндпоинты>
- derivation: <входные артефакты (id)>
- quality criteria: <критерии приёмки — пишутся ЗДЕСЬ, до исполнителя, не исполнителем>
- executable verification: <конкретная команда/скрипт, возвращающие pass/fail — см. ниже кто пишет>
- quality method: <тесты | схема | контракт-чек | LLM-судья по рубрике | человек>
- ownership: <файлы/модули, которые узел имеет право менять>
- resources: <вне git: БД, порты, внешние API | нет>
- tier: <A | B>
- budget: <оценка токенов/времени; максимум 3 попытки>
- cod: <число заблокированных потомков; на критической цепи? да/нет>
- version: <заполняется при приёмке: git-хеш коммита артефакта>
```

**Кто пишет executable verification (исполнитель — никогда):** модуль кода → отдельный test-agent пишет тесты ДО исполнителя, по контракту узла; схема/формат → валидатор схемы; конфиг/скрипт → смоук-команда от оркестратора; UI tier-A → build+lint+смоук как слой 1, содержательная проверка — человек по поведению; документ/ADR → LLM-судья по рубрике из quality criteria.

Размер узла: артефакт верифицируем за один проход; «ревью дольше генерации» = дели. Контекст-бюджет: входы + спека + релевантный код ≤ ~60% окна исполнителя.

### Gate-0 — СТОП

Покажи пользователю: верхний срез графа на бизнес-языке, критическую цепь, tier-A узлы, rework-буфер, ожидание по срокам, каденцию приёмки (согласуй слоты). Жди утверждения. Без Gate-0 исполнение не стартует.

## Фаза 2 — исполнение

Оркестрация: если в твоей сессии доступен Workflow tool — используй его (этот скилл = твой опт-ин; pipeline по готовности входов, НЕ волны с барьером). Если недоступен — параллельные Agent-вызовы (isolation: worktree, фоновые). Проверь фактическую доступность, не предполагая. Состояние узлов веди в `plan.md` (todo / running / awaiting-verify / awaiting-human / parked / done / failed) — статус хранит файл, не твоя память.

**Запуск узлов:**
- Узел стартует при: входы приняты ∧ паспорт полный ∧ есть WIP-слот.
- **WIP-лимит = min(3–5 активных узлов, пропускная способность верификации прогона).** Верёвка: очередь awaiting-human ≥ 2–3 → новые узлы НЕ стартуют. **Исключение — стартовые контракты (Gate-0.5):** все контракт-узлы первой волны идут параллельно и принимаются человеком одним батчем (единый слот); верёвка включается после Gate-0.5, иначе старт графа задушен сериальной приёмкой.
- Приоритет за слот, лексикографически: критическая цепь → straggler, разблокирующий fan-in → больше заблокированных потомков → FIFO.
- Бриф агенту узла = паспорт + входные артефакты + `handoffs/<input-id>.md` каждого входа + границы ownership + уроки learning loop по task-kind. КАК делать — решает агент; расширять scope узла запрещено.
- Таймаут узла = 2× медианной оценки; агент пишет прогресс в journal; тишина дольше таймаута = «застрял» → стоп + эскалация.

**Завершение узлов:**
- **Верификация двухслойная:** (1) executable verification из паспорта — детерминированно; (2) независимый агент-верификатор. **Промпт верификатора = ТОЛЬКО: паспорт узла + файлы артефакта + входные контракты. ЗАПРЕЩЕНО передавать: журнал работы, промпт исполнителя, число попыток, свои комментарии о качестве.** Формат ответа: по каждому quality criterion — PASS/FAIL + конкретное доказательство. Используй отдельный агент-тип критика/верификатора, не исполнителя.
- **Персистентность по умолчанию (урок 18.07.26, обрывы лимитов):** каждый промежуточный результат пишется В ФАЙЛ в момент получения, не в конце: артефакт — исполнителем сразу; вердикт верификатора — файлом `verifications/<узел>-attempt<N>.md` (верификатору дать право записи ЭТОГО файла; независимость обеспечивается контекстом, не запретом Write); смена статуса — строкой journal. Обрыв сессии/лимитов теряет максимум один незавершённый вызов, не результаты. Ретрай-логика: API-ошибка (лимит/сеть) ≠ попытка узла — счётчик попыток не инкрементится (отдельный cap суммарных вызовов).
- Провал → структурированный фидбек исполнителю, cap 3 попытки. **Эскалация** (после 3 провалов / merge-конфликт / застрял / abort): узел в parked, WIP-слот освобождается, человеку в ближайший слот — журнал попыток + диагноз + готовое предложение (другой подход / replan ветки / ручной фикс). Узел критической цепи — алерт сразу, не ждать слота. После провала обнови гейт/бриф, чтобы класс дефекта не повторился.
- **Merge сразу** после верификации. Новые узлы стартуют от обновлённой базы; уже работающие агенты доделывают на своей — при merge их результата: чистый rebase → ок; конфликт → СТОП + эскалация (разрешать «чтобы скомпилилось» запрещено); тесты узла красные после rebase без его изменений → это регрессия от соседнего merge = скрытое ребро → СТОП + эскалация. Конфликты систематически (>2 за прогон) → карта владения неверна → replan.
- **Правка shared-файла по ходу** (package.json, конфиг, barrel): не самоволие и не replan — запрос в очередь правок shared-артефакта, оркестратор применяет последовательно.
- **HANDOFF обязателен:** `handoffs/<node-id>.md`, формат: `## Decisions / ## Assumptions / ## Deviations / ## Input versions`. Без HANDOFF артефакт не считается сданным.
- **Abort mid-execution:** агент, понявший, что подход нежизнеспособен (рестарт от тех же входов бессмыслен), останавливается и эмитит abort + change-request с обоснованием — это сигнал, не расширение scope.
- Фейл узла = чистый рестарт worktree от тех же входов (никаких «дочинок» в грязном дереве).
- **Журнал атомарно со статусом:** каждое изменение статуса в plan.md = тут же строка в journal.md: `| время | узел | статус→статус | попытка | заметка |`.

**Человек в исполнении:**
- Приёмка tier-A — батчами в согласованные на Gate-0 слоты, по ПОВЕДЕНИЮ (запустить, потыкать), не по отчёту. Приёмщик недоступен >1 дня → tier-A НЕ деградирует до B; работа продолжается вне заблокированного поддерева.
- Статус = fever chart текстом: два числа + зона. `Принято на критической цепи: X из N (%). Rework-буфер сожжён: Y%.` Буфер горит быстрее цепи → жёлтая (реприоритизируй), сильно быстрее (>1.5×) → красная: СТОП, replan или срез скоупа — решение человека.
- Change-request (от завершённого узла или abort) → replan волной: оцени каскад инвалидации, человек утверждает дельту, версия графа +1.

**Инвалидация принятого:** артефакт признан дефектным после того, как на нём построились → каскад re-verify по потомкам, чей `## Input versions` ссылается на инвалидированную версию (и транзитивно), не по всему графу.

**Рискованные узлы — set-based**, критерий запуска 2–3 вариантов: spike не дал однозначного ADR, ИЛИ единственный подход висит на непроверенном допущении. Иначе — один вариант. Варианты разными подходами + узел-конвергенция по заранее заданным критериям; один вариант консервативный.

**Контекст оркестратора — фреймворк CTX v2 (19.07.26; доказательная база внешняя+внутренняя):**
- **Правило (выведено, не назначено): чекпойнт + сброс сессии на КАЖДОЙ границе волны.** Порог «300k» отброшен: (а) экономика — cache read = 0.1× base (платформа Anthropic) → налог контекста ≈ N/10 ток./ход, линейный, без клиффа; восстановление из файлов ≈ 60–100k однократно → break-even сброса на границе волны уже при N≈50k и ≥15 ходах следующей волны; (б) качество — Chroma Context Rot (18 моделей): деградация задолго до лимита, заметная с ~25% окна; NoLiMa (ICML'25): non-lexical retrieval у 11/12 моделей <50% уже на 32k; MECW: эффективное окно кратно меньше заявленного; для агентов context rot = первичный отказ. Обе оси голосуют за «сбрасывать часто», решает простота: граница волны = сброс.
- **Автоматика (действия человека ≈ 0):** SessionStart-хук `afm-checkpoint-inject.sh` (matcher * , вкл. clear/compact) сам инжектит CHECKPOINT.md активной программы в новую сессию — после /clear вводную вставлять НЕ нужно; PreCompact-хук `afm-precompact-guard.sh` блокирует АВТО-компакт при флаге `afm/<slug>/WAVE_ACTIVE` (mid-wave суммаризация без чекпойнта запрещена), ручной /compact не блокируется. /clear и /compact программно недоступны (факт платформы) — единственное действие человека = нажать /clear на границе волны по сигналу оркестратора; полная автоматика = CTX-2: headless-раннер «волна = свежая сессия» (claude -p --model <оркестратор>), внедрять после замера CTX-1.
- **Флаг волны:** старт волны → `touch afm/<slug>/WAVE_ACTIVE`; чекпойнт-ритуал границы (journal/plan/вердикты дописаны, CHECKPOINT.md обновлён, коммит) → `rm WAVE_ACTIVE` → сигнал «жми /clear».
- **/compact — аварийный инструмент mid-wave,** не рутина: сжатие до ~12% объёма лоссиво (summary), path-scoped правила теряются; применять с инструкциями («сохрани решения CEO, статусы узлов, активные красные зоны») и с восстановительным чеком после.
- **Восстановительный чек** (после clear И после compact): 5 письменных ответов только из файлов — статусы узлов; последние решения CEO дословно; открытое на людях; красные зоны; следующий шаг цепи. Промах = дефект CHECKPOINT.md, чинится файл.
- **Замер CTX-1:** расход волны до/после первого цикла + чек → факт сюда (рядом с нормативами моделей). Источники: platform.claude.com (кэш 0.1×/1.25×), code.claude.com/docs (context-window, hooks, headless), trychroma.com/research/context-rot, NoLiMa ICML'25, MECW-2025.
- **CTX-1 ФАКТ (19.07.26, граница волны 3 glass, первый боевой цикл):** (а) деградация — восстановительный чек 5/5 письменно только из файлов, без вводной пользователя, промахов не выявлено (CHECKPOINT.md отработал); (б) стоимость восстановления ≈100k контекста (64,5k cache-read + 37,8k cache-write + 10,7k out) ≈ $1.36 ≈ 2% сессионного лимита — одноразово, против налога хвоста прежней сессии >150k ctx на КАЖДЫЙ ход; (в) фон «до» (/usage 19.07 утро): неделя 54%, 70% расхода из сессий >150k контекста, 87% из subagent-heavy. «После» = расход волны 4 на чистом контексте — дописать при закрытии волны 4.

## Фаза 3 — интеграция и закрытие

1. **Интеграционный гейт — узел графа** (сборка + e2e + смоук по реальному сценарию, для UI — глазами под реальным логином). Критерий прохождения операционный: все сценарии паспорта гейта зелёные ∧ нет открытых re-verify ∧ все tear-допущения подтверждены verify-узлами ∧ открытые вопросы из HANDOFF разобраны. Локально зелёные артефакты ≠ работающая система.
2. **Ретро прогона — тоже узел** с DoD «уроки зафиксированы»: провалы верификации, правки человека, merge-конфликты, промахи оценок >2× → `loop.py record-trace → evaluate → distill` (или локальный аналог петли проекта). Факт-vs-оценка по типам узлов — в журнал, калибрует буферы следующего прогона.
3. **Отчёт пользователю** бизнес-языком: что принято (со ссылками), финальный fever chart, wall-clock vs критическая цепь (коэффициент реализации параллелизма), % принятых с первого раза, стоимость, уроки. Вердикт: можно ли запускать/сдавать сейчас и что осталось.

## Красные линии

- Узел без паспорта не стартует. Артефакт без верификации и HANDOFF не существует.
- Верификатор никогда не равен исполнителю; критерии приёмки и executable verification никогда не пишет исполнитель; верификатору не передаётся контекст производства.
- Очередь приёмки человека переполнена → не спавнить агентов (кроме батча контрактов Gate-0.5).
- Никакого батчинга готовых веток «до кучи» и big-bang merge в конце.
- Self-report агента («95% готово») статусом не является — только принятые артефакты.
- Один активный AFM-прогон на репозиторий.

## Экономика прогона (правило с 18.07.26 — ресурсы не терять)

**Маршрутизация по ролям (дефолт; правка CEO 19.07.26 — «штабной моделью становится opus, использование fable останавливается»):** test-агенты → sonnet/low; сборщики по замороженному контракту → sonnet/medium; статические верификаторы tier-B → sonnet + узкая рубрика (только критерии паспорта grep/схемами; поведенческий гейт = selftest на проде, «мысленная трасса всего кода» запрещена как пожиратель); **оркестратор/штаб, судьи tier-A, финальные адверсариальные аудиты, компиляция графа/паспортов, сводки человеку → OPUS** (штабная модель). **Fable — ОСТАНОВЛЕН как рабочая модель: подъём к нему = исключительный случай по явному решению CEO (причина: малые лимиты модели), с пометкой в журнале прогона.**

**Инструкции:** списки чтения — до разделов («C3 §2, §5», не файл целиком); один эталон кода; бриф ссылается на паспорт, не повторяет его; верификатору — рубрика+ownership без re-read всех входов; fail-fast: провал selftest'а чинит точечный sonnet-агент, не пересборка узла.

**Замер обязателен:** после каждой волны — факт токенов/узел в журнал прогона; отклонение от оценки >2× — в ретро и в калибровку бюджетов следующего прогона. Подтверждённые фактом нормативы стоимости узлов — вписывать СЮДА (ниже), они становятся дефолтными оценками Фазы 1.

**Нормативы по фактам прогонов** (пополняется замерами):
- growth-concept 17–18.07 (ДО оптимизации, топ-модель везде): D-узел ≈ 250–400k с судьёй; K-узел ≈ 300–500k с тестом и верификатором; вердикт fable-верификатора ≈ 60–236k. Это ВЕРХНЯЯ граница «как не надо».
- glass волна 1 (18.07, ДО v2, топ-модель+opus): 4 кодовых узла ≈ 1,05M/узел (вкл. 5 попыток A7 и фикс-агентов). База сравнения.
- glass AI-волна (18.07, ПОСЛЕ v2, sonnet везде): чистый узел (verified с 1-й) ≈ 0,33M — **−69% к базе**; узел с 3 ретраями из-за дефекта фикстуры ≈ 1,2M. Вывод: ретраи доминируют цену — качество селфтестов (уроки 174/175, полные починки в фикстурах) экономит больше, чем тир модели; sonnet на чистом прогоне не уступил по качеству (вердикты идентичной строгости).
- glass волна 2 (18.07, v2): 3 узла все с 1-й попытки ≈ 0,43M/узел (вкл. тест-фикс) — подтверждение −60%; норматив v2 для Фазы 1: кодовый узел ≈ 0,4–0,5M с тестом и верификацией.
- **glass волна 4 (19.07, v2, 4 узла) — расслоение по числу попыток, главный аргумент за фикстуры:** 3 узла с 1-й попытки (AI-2, AI-3a, AI-3b) = 1,03M / 3 ≈ **0,34M/узел** — ЛУЧШЕ норматива; 4-й узел (AI-3a.1) с 2 провалами сборки + 4 верификациями = **0,97M на один узел**, втрое дороже чистого. Плюс 2 фикс-агента прод-селфтестов (176k + 105k) — оба дефекта оказались В ТЕСТАХ, не в коде (пул id захардкожен 60 при плане 334; строка типов `bind_param` 11 символов на 12 плейсхолдеров). Итог волны 2,28M / 4 узла ≈ 0,57M/узел. **Вывод третий раз подряд: цену волны определяют не тир модели и не размер узла, а качество фикстур и полнота критериев в паспорте.**
- **Норматив верификации ПДн-узлов (новое, урок 179):** узел, чей критерий — «временные данные удалены», требует в паспорте ЯВНОГО указания «доказательство = find по диску, не ls каталога»; иначе верификатор ловит расхождение на 3-й попытке и цена узла удваивается.
