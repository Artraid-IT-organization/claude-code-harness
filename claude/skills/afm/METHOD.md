## 0. Суть

Проект — не последовательность задач, а **DAG артефактов**: конечных, проверяемых состояний (схема БД, API-контракт, модуль, тест-сьют, документ, ADR). Работа над узлом стартует, как только готовы все его входные артефакты — не по календарю и не по волнам с барьером. Оптимизируется скорость появления **принятых** (верифицированных) артефактов на критической цепи, а не количество закрытых задач и не занятость агентов.

Три кита, на которых всё держится (убери любой — метод разваливается):
1. **Паспорт узла до старта** (full-kit): без полной спеки и приёмочных критериев агент не запускается.
2. **Независимая верификация на границе узла**: артефакт становится входом потомков только после гейта; verifier ≠ producer.
3. **Ограничение — человек-приёмщик**: весь параллелизм подчинён его пропускной способности (drum), иначе выигрыш испаряется в очереди приёмки.

## 1. Модель графа

### Узел = артефакт с паспортом
Паспорт (по образцу PRINCE2 Product Description) обязателен ДО старта узла:

| Поле | Что содержит |
|---|---|
| purpose | зачем артефакт, ЦКП одной фразой |
| composition | что именно входит в результат (форма: файл, таблица, эндпоинт) |
| derivation | входные артефакты = входящие рёбра DAG (с версиями после их приёмки) |
| quality criteria | машинно-проверяемые критерии приёмки (написаны НЕ будущим исполнителем) |
| quality method | чем проверяем: тест / схема / контракт-чек / LLM-судья по рубрике / человек |
| ownership | карта владения: какие файлы/модули узел имеет право менять |
| resources | ресурсы вне git: БД, порты, внешние API, миграции |
| tier | A = принимает человек (по поведению), B = автоматика + выборочный контроль |
| budget | токены / время / максимум попыток (cap 3 → эскалация, см. §3) |
| cod | данные приоритета: число заблокированных потомков; на критической ли цепи (порядок свёртки — §3 «Приоритет») |
| version | заполняется при приёмке: git-хеш коммита артефакта; потомки фиксируют версии входов в своём HANDOFF |

Правила узла:
- **Состояние, не действие.** «Исследовать X» — не узел; узел — «ADR по X принят». (Andersen: milestone = состояние.)
- **Размер**: артефакт верифицируем за один проход; «ревью дольше генерации» = дели. Норматив: часы, максимум 1–2 дня агентной работы.
- **Контекст-бюджет**: входы + спека + релевантный код ≤ ~60% контекстного окна исполнителя (грубая прикидка по объёму файлов); переростки дробить.
- **Идемпотентность**: фейл = чистый рестарт worktree от тех же входов. Артефакт «либо принят, либо не существует».

### Ребро = информационная зависимость
- Тест ложного ребра: «изменится ли содержимое B, если A выйдет другим?» Нет → ребра нет.
- Скрытые рёбра, которых нет в логике, но есть в жизни: **общие файлы** (роутинг, конфиги, lockfile, миграции, barrel-экспорты) и **общие внешние ресурсы** (одна dev-БД, один API-лимит). Пересечение карт владения двух узлов = принудительное ребро сериализации, даже если логически они независимы.
- Merge-конфликт, падение интеграции, красные тесты после rebase без изменений узла — всё это сигнал невыявленного ребра → дописать ребро в граф и урок в learning loop.

### Граф целиком
- **100% rule**: сумма листовых артефактов = 100% результата, без дублей и дыр (иначе два агента сделают одно и то же или никто не сделает стык).
- **Иерархия**: ≤ ~20–30 узлов на уровень; крупный узел раскрывается в подграф. LLM-планирование деградирует к ~0% оптимальности на 50+ узлах (Plan-over-Graph) — граф валидируется кодом/чек-листом, не «на глаз».
- **Rolling wave** (волна ПЛАНИРОВАНИЯ — не путать с исполнением: исполнение всегда по готовности входов, без барьеров): полные паспорта — только у ближайшего горизонта; дальше — planning-packages (цель + бюджет, без декомпозиции). После ключевых артефактов — replan-gate: граф достраивается, человек утверждает только дельту.
- **Wicked/discovery-территория**: если проблема понимается только через решение — в граф идёт только spike-узел (выход = ADR/прототип), продолжение рисуется после его приёмки. Глубокий DAG по неизведанному = фикция.

## 2. Компиляция графа (до исполнения)

Порядок обязательный — каждый шаг закрывает конкретный класс провалов:

1. **Инвентаризация артефактов** из цели проекта (бизнес-язык, верхний срез обозрим за раз).
2. **Рёбра**: информационные зависимости + тест ложного ребра.
3. **DSM-проход на циклы**: найти взаимозависимые пары/группы (схема БД ↔ API). Цикл не растягивать в цепочку: либо слить в один узел, либо **tear** — разорвать артефактом-допущением (контракт, стаб, draft-схема), у которого ниже по графу стоит обязательный verify-узел «допущение подтвердилось». Tear без verify = тихий техдолг.
4. **Контракт-первым**: интерфейсы (API-спека, схема БД, типы, форматы) = первые узлы графа, tier A, замораживаются до fan-out. Контракт фиксирует минимум (интерфейс, не реализацию — set-based minimum constraint). Смена контракта после старта потребителей = формальный replan, не тихая правка.
5. **Карта владения**: каждому узлу — непересекающийся набор файлов/модулей. Общие точки — в отдельный ранний артефакт. Общий внешний ресурс → сериализация или изоляция (БД-на-worktree).
6. **Tier-разметка**: propagation cost (сколько системы затронет изменение артефакта) определяет tier A — схема БД и core-контракты принимаются человеком раньше и жёстче всех.
7. **Критическая цепь**: самый длинный путь с учётом **ресурсов** (слоты приёмки человека, квоты API), не только рёбер. Оценки узлов — медианные, вся страховка — в едином rework-буфере проекта. Стартовый размер буфера: 30–50% длины критической цепи (CCPM-эвристика: ~50% от суммы срезанных «хвостов» оценок); после первых прогонов — из телеметрии факт-vs-оценка. Размер утверждается на Gate-0.

Выход компиляции: `plan.md` (реестр узлов + статусы + версия графа) и `passports/`. Gate-0: человек утверждает граф и rework-буфер.

## 3. Исполнение

- **Готовность ≠ запуск.** Узел стартует при: входы приняты ∧ паспорт полный (full-kit) ∧ есть WIP-слот.
- **WIP-лимит** = min(3–5 активных узлов, ёмкость верификации). Правило верёвки (DBR): очередь на приёмку человека ≥ 2–3 артефакта → новые узлы НЕ стартуют, даже если входы готовы. Утилизация 100% = экспоненциальные очереди; резерв ёмкости — это и есть скорость.
- **Приоритет** при конкуренции за слот — лексикографически: (1) узел на критической цепи, (2) straggler, разблокирующий fan-in, (3) больше заблокированных потомков, (4) FIFO как tie-break.
- **Изоляция**: worktree на узел, живёт часы. Агент пишет только внутри своей карты владения.
- **Правка shared-файла по ходу работы** (package.json, конфиг, barrel-экспорт — возникает в большинстве реальных узлов): не replan и не самоволие — микро-координация: запрос в очередь правок shared-артефакта, оркестратор применяет их последовательно (sequential merge), узлы получают обновлённую базу через rebase.
- **Merge немедленно** после верификации (trunk-based, малые партии). Копить готовые ветки «до кучи» запрещено — каждый принятый merge меняет базу, активные узлы ребейзятся сразу. Merge-конфликт = стоп + эскалация; агенту запрещено разрешать конфликт «чтобы скомпилилось». Отдельный случай: после rebase тесты узла краснеют без его изменений — это регрессия от соседнего merge = скрытое ребро → стоп + эскалация, не «починить у себя».
- **HANDOFF**: каждый артефакт сопровождается компакт-файлом «принятые решения / допущения / отклонения от спеки / версии входов» — он входит в контекст всех потомков. Передача через файловую систему, не через пересказ.
- **Надёжность**: таймаут узла = 2× медианной оценки; heartbeat = запись прогресса в журнал (нет записей дольше таймаута = «застрял» → стоп). Состояние графа хранит файл/движок, не память чата. Журнал прогона: узел, входы (версии), вердикт, попытки, стоимость.
- **Abort mid-execution**: агент, понявший посреди работы, что подход нежизнеспособен (рестарт от тех же входов бессмыслен), обязан остановиться и эмитить abort + change-request с обоснованием. Это не расширение scope, а сигнал; узел паркуется до решения.
- **Эскалация** (единый маршрут для: 3 проваленных попыток, merge-конфликта, «застрял», abort): пакет человеку в ближайший слот приёмки — журнал попыток + диагноз + готовое предложение (другой подход / replan ветки / ручной фикс). Слот WIP освобождается, узел в статусе parked. Если узел на критической цепи — алерт немедленно (relay-runner), не ждать слота.

## 4. Качество (Jidoka)

- **Двухслойная верификация** каждого узла: слой 1 — детерминированный гейт (тесты, схема, линт, контракт-чек) как код, не как просьба агенту; слой 2 — независимый LLM-верификатор по рубрике из quality criteria, со свежим контекстом, видит контракт, но не ход работы. Verifier ≠ producer — всегда.
- **Stop-the-line + 4-й шаг**: провал гейта останавливает нисходящую ветку И обязует обновить гейт/бриф так, чтобы класс дефекта не повторился — иначе параллельные агенты растиражируют одну ошибку по всем веткам. Фидбек исполнителю — структурированный (что именно не так), cap 3 попытки → эскалация (§3).
- **Инвалидация принятого**: артефакт признан дефектным после того, как на нём построились → каскад re-verify по потомкам, чей HANDOFF ссылается на инвалидированную версию входа (и транзитивно дальше по той же логике) — версия артефакта (git-хеш) делает границу каскада вычислимой.
- **Интеграционные гейты — узлы графа** (сборка, e2e, демо человеку). Критерий прохождения операционный: все сценарии из паспорта гейта зелёные ∧ нет открытых re-verify ∧ все tear-допущения подтверждены своими verify-узлами ∧ открытые вопросы из HANDOFF-файлов разобраны. Локально зелёные артефакты не гарантируют сходимость системы.
- **Set-based для рискованных узлов** — критерий запуска 2–3 параллельных вариантов: spike не дал однозначного ADR, ИЛИ единственный известный подход висит на непроверенном допущении. Варианты разными подходами + узел-конвергенция с заранее заданными критериями выбора; один вариант — консервативный fallback. Иначе — один вариант (2–3× токенов без критерия — расточительство).

## 5. Человек: три точки + протокол

Точки: **Gate-0** (утверждение графа), **приёмка tier-A** (по ПОВЕДЕНИЮ — запустить и потыкать, не по отчёту агента), **внешние факты** (доступы, деньги, люди). Всё остальное — автономно.

- **Каденция**: приёмка батчами в 2–3 фиксированных слота в день, не по прерыванию. Relay-runner-алерт: «артефакт критической цепи придёт на приёмку через ~N минут» — критическая цепь не ждёт в очереди.
- **Приёмщик недоступен** (>1 дня): tier-A автоматически НЕ деградирует до B — планка приёмки ключевых артефактов не размывается ради скорости. Исполнение продолжается на ветвях вне заблокированного поддерева; fever chart уходит в жёлтую зону; накопившиеся tier-A принимаются батчем по возвращении.
- **Fever chart** — единственный статус проекта: X = % ПРИНЯТЫХ артефактов критической цепи, Y = % сожжённого rework-буфера. Зелёная зона — агенты автономны; жёлтая — реприоритизация; красная — эскалация: replan или срез скоупа. Self-report агентов «почти готово» статусом не является.
- **Replan**: change-request (от завершённого узла или abort работающего) → ре-план волной с оценкой каскада инвалидации; человек утверждает дельту; версия графа инкрементируется.

## 6. Learning loop (зашит в контур)

- Перед узлом: recall уроков по task-kind узла (при первом прогоне — стартовые дефолты этого документа).
- Триггеры захвата урока: провал верификации, правка человеком принятого артефакта, merge-конфликт, найденное скрытое ребро, промах оценки >2×. Захват = record-trace → evaluate → distill.
- Ретро прогона — узел графа с собственным DoD («уроки зафиксированы, гейты/шаблоны обновлены»).
- Телеметрия факт-vs-оценка по типам узлов (EMA) калибрует буферы следующих прогонов.

## 7. Метрики

Главные: **lead time узла** (паспорт → принят), **flow efficiency** (время генерации / lead time — остальное очереди), **% принятых с первого раза**, **wall-clock прогона / длина критической цепи** (коэффициент реализации параллелизма). Вспомогательные: wait по состояниям узла (waiting-inputs / generating / awaiting-verify / awaiting-human / parked), stragglers, merge-конфликты за прогон, стоимость в токенах на принятый артефакт. Занятость агентов метрикой НЕ является.

## 8. Границы применимости — когда AFM НЕ применять

- Задача < ~5 артефактов, правка в 1–2 файла, ресёрч без известной формы результата → прямое исполнение; оверхед компиляции графа больше самой работы.
- Сильно связное ядро без реальной ширины (Anthropic: кодинг — худший кейс мультиагентности при высокой взаимозависимости) → один агент последовательно; AFM даёт выигрыш только на графе с реальной шириной ≥ 3.
- Wicked-территория целиком → сначала spike-узлы, граф рисуется по мере понимания (rolling wave), не целиком заранее.
- Один активный AFM-прогон на репозиторий: карты владения двух прогонов неизбежно пересекутся; второй прогон — в очередь или в другой репозиторий.

## 9. Экономика и модель выигрыша

Числа ниже — стартовая калибровка ожиданий для Gate-0; после первых прогонов заменяются собственной телеметрией.

- Потолок ускорения: S_max = T_seq / T_crit (сумма всех узлов / критическая цепь).
- Реальные срезы потолка: WIP-cap 3–5, полоса приёмки человека (drum), merge tax (растёт ~квадратично с шириной), оверхед координации и верификации.
- Стоимость: 3–5× токенов против одиночного последовательного чата (fan-out + независимая верификация); ресёрч-класса fan-out — до 15× (Anthropic).
- Ожидание для типовой крупной доработки (~20–30 узлов, ширина 4–6, критическая цепь 30–40% суммы): **wall-clock 2–3×** быстрее линейного чата при выделенных слотах приёмки; без дисциплины слотов выигрыш падает к ~1.5× — упирается в человека, а не в агентов.
- Второй (часто больший) эффект — срез переделок: 42% провалов мультиагентных систем — неоднозначная спека (Berkeley/CMU, 2025; закрывается паспортом full-kit), каскадное размножение ошибок (закрывается гейтом на границе узла).
