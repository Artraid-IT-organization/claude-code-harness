# Отчёт о проделанной работе

Канон проекта — `~/reports`. Этот скилл — короткая инструкция; правила и источники живут там
и обновляются по мере правок владельца.

## Порядок

**1. Прочитать канон.** `~/reports/METHOD.md` (как писать) и `~/reports/SOURCES.md` (откуда факты).
Не собирать отчёт по памяти о прошлых отчётах: правила менялись.

**2. Определить период.** Недельный — прошедшая неделя до вчера включительно. Дневной — сегодня.
Если сомнение в границах, взять дату явно из запроса, а не угадывать.

**3. Собрать фактуру.**

```bash
~/reports/tools/collect_facts.sh ДАТА_ОТ ДАТА_ДО     # конец не включается
```

Затем прочитать снапшоты состояния из `SOURCES.md` — цифры берутся оттуда, а не из формулировок
коммитов. Проверить `~/downloads` на входящие документы за период: календари от CEO, ТЗ,
замечания отдела продаж. План на следующий период строить по самой свежей версии календаря,
назвав в отчёте её дату.

**4. Написать `.md`** в `~/reports/archive/ГГГГ-ММ-ДД-тип.md` по структуре из `METHOD.md`.
Скелеты: `~/reports/templates/weekly.md`, `daily.md`.

**5. Собрать, вычитать, отправить.**

```bash
cd ~/reports
python3 tools/md2docx.py archive/ФАЙЛ.md archive/ФАЙЛ.docx
python3 tools/docx2md.py archive/ФАЙЛ.docx -          # вычитка глазами получателя
python3 tools/send_tg.py archive/ФАЙЛ.docx "Подпись одной строкой"
git add -A && git commit -m "отчёт: ..." && git push
```

## Что делает отчёт правильным

- Единица отчёта — новая возможность системы или измеримый результат, а не проделанная работа.
  Не «улучшена функция X», а «менеджер теперь делает Y, объём Z».
- Сухой доклад. Никаких аллегорий и возвышенных оборотов: такой текст читается как машинный,
  и руководство перестаёт вчитываться.
- Кавычки-ёлочки « » не использовать вообще. Названия систем и воронок — без кавычек.
- Любой процент со знаменателем в той же фразе.
- Объём в бизнес-единицах: заявки, заказы, звонки, рубли, экраны. Не в коммитах и файлах.
- Ни одного утверждения без подтверждения в доке, гейте или журнале. Приписанная себе заслуга
  или задача из плана, которой нет в git, — брак.
- Финальный вердикт: можно ли запускать, что держит.

## Перед отправкой

Проверить на готовом файле: нет ёлочек, нет остатков `**`, кириллица целая, таблицы на месте,
проценты со знаменателем, нет внутренних кличек и хешей. Отправка — действие наружу:
если в отчёте есть спорный факт, сказать о нём владельцу, а не отправлять молча.
